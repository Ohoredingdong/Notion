# 생활 화면과 실제 사용 동선

사용자는 영양제가 냉장고 바로 위에 보이고,8개 레시피를 정보를 비교한 뒤 고르며, 건강상식·꾸미기·음식 그림일기·식비에 쉽게 접근하기를 요청했다. `feat/kitchen-living-dashboard-20261106`에서 `2f73482d`를 기준으로 구현한다. 기존 사진·v1 저장 키·정상 동작·운영 금융 갱신은 보존하며 main 병합·운영 배포는 하지 않는다.

## 구현한 동작

- **냉장고:** 넓은 위젯은 위쪽 빈 수납장 공간에 실제 등록 제품의 오늘 체크 선반을 둔다. 작은 위젯은 상단의 영양제 요약44px 버튼에서 복용 기록으로 이동한다. 오늘 체크와 다른 날짜 기록을 구분하고0개는 등록 안내를 보여 준다. 제품을 임의로 추가하지 않는다.
- **레시피:**8개 카드에 사진·전체 이름·시간·입력 열량/원가·수량/기한을 확인한 재료 충족 수를 표시한다. 모르는 값은 `—`로 두고 미입력 의미를 명시한다. 목록·필터를 상단에 통합해 작은 화면에도8개를 유지한다. 카드 선택 뒤 상세·찜·계획·실제 식사 흐름은 이어진다.
- **기록:** 기본 화면은7열×6주 달력이다. 실제 음식 사진·추가 기록 수를 날짜에 표시하고 누르면 그날의 그림일기에서 식사·영양·분량을 본다. 빈 날짜에 가짜 식사를 넣지 않는다. 다음 기록 진입은 다시 달력에서 시작한다.
- **식비:** 기록 첫 화면 하단에 선택 월의 실제 지출·남은 예산을 표시하고 식비 탭도 두 번째 위치에 둔다. 장보기 예상과 실제 구매·지출을 구분한다. 지출 저장은 재고 입고와 별도이며 기존 거래 모델을 사용한다.
- **내 부엌:** 꾸미기가 기본이다. 같은 방 사진에서 소유·기본 소품 선반, 선택 물건, 배치 도구, 취소·적용을 본다. 다른 탭으로 이동하면 초안을 취소하고 자동 적용하지 않는다. 기존 좌표를 보존하며 새 기본 소품만 조리대에서 시작한다. 드래그·키보드 이동·보상 비용/소유권을 유지한다.
- **건강상식:** 내 부엌의 꾸미기·도감·건강상식·설정 네 탭 중 하나다. 영양표시·알레르기 표시·보관·영양제 기록의 읽을거리를 제공하며 참고 출처는 식품안전나라로 표시한다. 공식 자료를 실시간 수집하거나 개인 건강 상태를 판정한 결과가 아니다.

## 검증 자료

[최종 생성물 해시](kitchen-living-20261106/build-manifest.json), [실행 결과](kitchen-living-20261106/verification.json), [기존 자료 보존](kitchen-living-20261106/preservation.json), [실제 화면 모음](kitchen-living-20261106/screens.png)을 함께 확인한다. 제품·식사·지출이 있는 캡처는 격리된 명시적 QA 입력 예시이며 기본 제품 데이터에 넣지 않는다. 원본 PNG와 동일 자료의 전후 화면도 증거 폴더에 보존한다.

화면 모음은 실제 캡처6개를 균일 비율로 나란히 놓은 것이다. 개별 PNG는 실제 위젯 경계로만 잘랐으며, 전체 호스트 원본은 아래 외부 실행 폴더에 보존한다. 음식 달력과 식비 모음은 같은 입력 상태의128,000원 지출·172,000원 잔액이며, 실제 구매20,000원 저장 후148,000원·152,000원 검증은 별도 거래 결과와 `budget-saved.png`로 구분한다.

최종 고정4파일에서 생활 화면49사례·7,953단언과 실제 식비2사례가 모두 통과했다. 기존 Node233건·전송12건도 통과했다.49사례에는 빈 위젯20·입력 위젯8·앱2, 영양제 날짜6/실제 등록2, 꾸미기 거래4, 기존 v1 원문1, 실제 식사 저장/차감/취소/재저장6이 포함된다. 보호한 데이터·자산·워크플로·핵심 모델 등535경로의 원문은 같다. 최종 QA 해시와44개 제품/생성 소스·4HTML의 일치는 별도 provenance로 확인했다.

새 회귀는 native/opaque의 작은 임베드·긴 휴대폰·넓은 호스트·599/600 영양제 전환 양쪽, 빈 상태와 입력 상태, 앱 두 크기를 검사한다. 주요 조작44px, 조밀한 달력 날짜24px, 가로 넘침·텍스트/사진 가림·실제 클릭·기존 원문 보존을 구분한다. 영양제 실제 등록/체크/되돌리기, 꾸미기 미리보기·취소·1회 비용/무료 소유 재배치, 실제 식사 저장·5개 재고 차감·취소·재저장과 기존 v1 원문도 실행한다. 식비는 별도 native/opaque390에서 실제 구매 검수→지출 저장→달력/식비 월 집계·예산 잔액·별도 입고를 검사한다.

두 root는 기존 생성기로 만든 고정 native/app·위젯 및 mobile4파일이다. 소스와 생성 파일은 실행 중 바꾸지 않는다. 현재 네 화면 모두 요청에 따라 달라졌으므로 이전 화면과 픽셀 차이0을 요구하지 않고 같은 데이터/크기/동선의 전후 캡처를 검토한다. 과거 `test_kitchen_widget_browser.py`의 B1 내부 필터와 영양/도감 기본 탭 가정을 새 계약으로 잘못 적용하지 않는다. 기존 저장·거래 단언은 새 회귀에서 보존한다.

첫 고정 후보에서는 앱의34/36/42px 하위 탭과 좁은 앱 건강상식 출처 가림을 실제로 발견했다. 앱 탭44px과 건강 카드/부모 flex 높이를 고친 뒤 별도6크기 소스 프로브를 수행했다. QA도 body의 `data-home-page`를 건강 section으로 잘못 선택한 부분과1px 외곽 border 경계 계산을 명시적으로 바로잡았다.44px·본문 가림 검사는 유지하고 각 건강 카드 안의 실제 텍스트 경계 검사도 추가했다. 초기 실패는 외부 `living-final-v1/`에 보존하며 제품 문제와 QA 정합 문제를 구분한다.

두 번째 실행에서는 기존 앱 프레임의 소수점 높이를 `clientHeight` 정수로 잘라 계산한0.09375px 경계 오차를 재현했다. 스크롤바가 없는 hidden/clip 영역만 DOMRect에서 실제 border를 빼서 계산하고, scroll/auto의 실제 viewport는 유지하도록 QA를 바로잡았다.44px·본문 검사와 기존1px border 허용치는 바꾸지 않았다. 이 단계에서 제품과 고정4HTML은 변경하지 않았고 `living-final-v2/` 실패·별도 앱 원인 대조도 보존했다.
