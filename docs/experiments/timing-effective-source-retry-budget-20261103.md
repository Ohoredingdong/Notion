## One falsifiable fault hypothesis, one repair candidate
The bounded autopilot policy states `maximum_source_attempts=2`, implemented in `SafeCollector`. But `original.process` calls `stock_forecast_sources.history`, which invokes `read_history_serially` and internally retries cache locks **up to three times**. Thus a synthetic persistent database lock may execute six underlying fetcher invocations over two logged autopilot attempts; the outer report may underdescribe effective retry volume. This is a source/circuit-breaker accounting risk, not proof it has occurred in real runs or that yfinance makes exactly one network request per fetcher invocation.

**Predeclared RED:** Add a dependency-only synthetic test that executes the genuine `SafeCollector` + `read_history_serially` path with a fetcher raising the known cache-lock exception. Require no more than the precommitted two fetcher invocations for a bounded autopilot group; otherwise fail. Controls must show standalone nonautopilot reader retains its existing three-try cache-lock recovery, unknown errors are never retried, no quote/old data is substituted, and sequential calls cannot leak a retry-context override.

**Permitted GREEN if RED reproduces:** One narrow scoped context guard: when `SafeCollector` owns bounded retries, the lower-level `read_history_serially` performs only one fetcher invocation, so each outer attempt consumes at most one cache-lock fetcher call. Outside that context preserve existing reader lock-retry behavior. The guard must reset in `finally` even on unexpected exceptions. Do not alter the authorised two outer attempts, rate limit cooldown, nontransient status classification, market-session no_call, predictive thresholds, shadow catalogue, strict-green, prices, outcomes, learning, issuance, published code or user-order settings.
