# 생활형 부엌 — 앱·위젯 재디자인 1차

> **사용자 거절 후 보존하는 이전 구현 기록이다.** 사용자는 이 시안을 거절하고, 보내준 사진처럼 입체적인 미니어처 부엌·식재료·소품을 직접 만지는 방향을 선택했다. 허브·잎 보상 UI나 이 문서의 배치를 승인된 최종 디자인으로 재사용하지 않는다. 최신 시각 검토는 [미니어처 부엌 시안](MINIATURE_KITCHEN_DESIGN.md)을 따른다. 아래 테스트는 이전 구현의 실행 증거이며 디자인 승인 증거가 아니다.

사용자의 최신 요청에 따라 두 화면을 다시 설계하고, 재료를 관리하는 부엌에 목표·성장·선택과 생활 기록을 더했다. 기준은 `2a8b8ae`, 작업 브랜치는 `feat/kitchen-life-redesign`이다. 이전 인수인계의 ‘첫 작업은 분석만’ 이후 사용자가 디자인·양념·두 버전 구현을 연속 요청한 후속 작업이다. 기존 앱 경로와 저장 원본은 보존한다. main 병합·Pages 배포·모바일 앱 출시를 뜻하지 않는다.

## 화면과 크기

- **앱:** 부엌 홈·오늘의 추천 메뉴와 기존 재고를 유지하고, 사진 등록 / 꾸미기·성장 / 식비 / 영양·영양제 / 월간 기록을 추가했다. 데스크톱은 두 열, 모바일은 한 열이다.
- **위젯:** 같은 기능·그림·데이터를 사용한다. 기본 상한 폭 720px, 권장 검토 크기는 약 560×760px다. 320px 폭도 지원하되 화면을 세로로 스크롤한다. 기능을 전부 한 화면에 밀어 넣지 않는다. 위쪽 생활 메뉴는 가로 스크롤, 냉장고/양념/재고는 원래의 선택 버튼이다. 성장 카드는 냉장고 아래에 둬 첫 화면을 가리지 않는다.
- 위젯 냉장고 기본 장면 높이는 800px, 본체는 580px다. 저장하지 않은 기본 재료는 2열로 놓고 같은 선반 재료가 늘면 높이를 확장한다. 이미 저장한 좌표·겹침·층 순서는 바꾸지 않는다.
- 위/아래 칸이 한 화면에 들어오지 않으면 재료를 끈 채 화면 가장자리에서 기다려 스크롤한다. 기존 보관 위치 버튼·키보드 이동도 유지한다.
- 기존 밝은/어두운 모드 선택을 유지하고 새 생활 카드의 대비도 확인한다.

## 기록과 계산의 경계

새 저장 키 `use-me-first-life-v1`은 기존 `use-me-first-state-v5`·냉장고 위치·양념 배치와 분리된 **추가 기록**이다. 기존 키를 옮기거나 지우거나 이름을 바꾸는 마이그레이션은 없다. 읽기만으로 새 키를 만들지 않는다. 두 진입점은 같은 출처에서 실행할 때 같은 키를 사용한다. 미리보기와 GitHub Pages처럼 출처가 다르면 기존 기록이 자동 전달되지 않는다.

- 새 키의 version 1에는 선택한 목표·테마·보상 수령일, 월 예산, 직접 정한 하루 목표, 식비 항목, 수동 영양 기록, 영양제와 체크 날짜가 들어간다.
- 새 생활 기록은 **이 브라우저 로컬 저장만** 지원한다. 기존 재료 동기화에 포함되지 않는다. 화면에도 이를 표시한다. JSON 내려받기는 이 새 키의 내용만 내보내며 기존 식사·재고·위치·사진은 포함하지 않는다. 가져오기 UI는 아직 없다.
- 형식이 깨지거나 이후 버전이면 원본을 덮어쓰지 않고 저장 실패를 알린다. 할당량·권한·잠금 실패도 저장 성공으로 보고하지 않는다. 가능한 브라우저에서는 Web Locks로 최신 값을 다시 읽어 저장한다. Web Locks 미지원 환경의 동시 탭 충돌 방지는 완성되지 않았다.
- 수동 영양 입력은 `source:manual`이다. 빈칸은 `null`, 확인한 0은 `0`으로 구별한다. 오늘 합계 옆의 입력 건수는 해당 성분을 입력한 건수/전체 영양 입력 건수다. 미입력 부분을 0으로 채우지 않는다.
- 월간 비율은 탄수화물·단백질·지방이 모두 있는 기록만 사용해 4/4/9kcal/g으로 환산한다. 전체 섭취량·공식 권장 비율·건강 평가로 표시하지 않는다. 식사 기록 수와 별도로 수동 영양 기록을 넣을 수 있으므로 서로 연결됐다고 가정하지 않는다.
- 식비는 사용자가 입력한 지출 합계다. 미기록 지출을 알 수 없으며, 기존 ‘우리의 식탁/돈’의 계획값·실제 값과 자동 병합하지 않는다. 월 예산은 현재 설정한 공통 목표이며 월별 목표 이력은 아직 없다.
- 성장 보상은 현지 날짜별 1회다. 재료 확인은 사용자 자기 확인, 식사/식비 목표는 해당 날짜 실제 저장 기록이 있어야 수령한다. 약 복용·적게 먹기·지출 늘리기를 보상 조건으로 삼지 않는다. 잎은 현금이나 유료 재화가 아니다.

## 사진 자동화의 다음 구현

현재 사진은 `blob:` 미리보기로만 사용하고, 저장·업로드·분석하지 않는다. 파일 교체·페이지 종료 시 URL을 해제하고 잘못된 형식·12MB 초과·디코딩 오류를 알린다. 실제 휴대폰 카메라·HEIC는 미검증/미지원이며, 카메라와 파일 선택 방식은 브라우저에 따라 다르다.

다음 단계는 두 흐름을 같은 검수 절차로 연결한다.

1. **제품 2장:** 하나의 등록 세션에 제품 사진과 기한 사진을 묶는다. 상품명·포장 단위·표시 기한 종류·읽은 원문·후보 날짜·인식 신뢰도를 반환한다. 촬영일을 소비기한으로 사용하지 않는다.
2. **초기 냉장고 1장:** 보이는 재료 후보 목록을 제안한다. 가려진 재료·잔량·유통기한을 추정 사실로 저장하지 않는다. 중복 후보를 사용자가 합치거나 삭제한다.
3. **검수:** 후보마다 이름·수량/단위·냉장/냉동·소비기한을 수정한다. 모호한 날짜는 직접 선택한다. 확인한 후보만 새 lot로 저장하며 기존 재고를 대체하지 않는다.
4. **아이콘:** 사용자 사진에서 배경을 분리하거나 같은 무드로 생성한 아이콘을 후보에 연결한다. 실패하면 기존 재료 그림을 사용하고, 생성 성공과 재고 저장 성공을 분리한다. 현재 수동 등록은 기존 그림만 사용한다.
5. **실제 연결:** 인식/생성 제공자·비용·응답 형식과 실패·시간 초과·재시도 정책을 정하고 서버 함수에 연결한다. 인증키는 서버 환경에만 보관한다. 사용자 사진을 보내기 전에 실제 업로드 동의, 메타데이터 제거, 보관/삭제와 접근 권한을 구현·검증한다. 현재 저장소에는 이 인식 백엔드가 없다.

`use-me-first-life.css`는 공통 새 디자인과 읽기 쉬운 위젯 배치, `use-me-first-life-model.js`는 선택적 생활 저장·검증·월간 계산, `use-me-first-life.js`는 같은 화면·폼·사진 미리보기를 담당한다. 기존 네 페이지·DOM·이벤트를 유지하고 내비게이션에 생활 화면 5개를 더했다. 위젯 파일과 단일 HTML은 원본에서 생성한다.

```bash

python scripts/test_fridge_presentations_browser.py --root "$PWD" --output /tmp/kitchen-widget-regression
```

회귀에서 이전의 ‘장면 높이 500px 미만’ 단언은 새 요구와 충돌하므로 800px 이상·재료 44px 이상·문 디스플레이 12px 이상으로 교체했다. 페이지 개수는 4→9로 갱신하고 새 페이지도 단일 노출·활성 메뉴를 검사한다. 터치 검증은 화면 밖 목적지를 가장자리 자동 스크롤로 드러낸 후 이동하며, 좌표 저장 단언을 유지한다. 저장 중 폼 입력·체크 버튼을 잠궈 빠른 연속 입력의 유실을 방지한다.
