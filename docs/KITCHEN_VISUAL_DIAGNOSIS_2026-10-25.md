# 냉장고 화면이 어색해진 원인 점검

2026-10-25 사용자 요청: “왜 이상해졌는지 체크해봐”. 조사 대상은 `a88ff745`의 미니어처 시안이며 확대 전 `375c8f86`과 비교했다. 배치·이미지·미리보기 파일은 이번 점검에서 추가 변경하지 않았다.

결론은 **냉장고 확대를 전체 장면·뷰포트·반응형 전환과 함께 조정하지 못했다**는 것이다. 그림 파일이 로드되고 문과 드래그가 작동하는 것만으로 화면 구도가 정상이라고 판단할 수 없었다.

## 재현 방법과 범위

- 현재 전달 HTML이 HEAD의 생성 HTML과 이미지 인코딩 외에는 같은지 확인했다.
- 이전 코드의 5개 이미지 URI만 현재와 같은 내장 이미지로 치환해, 그림 품질 차이를 제외하고 배치 변경을 비교했다.
- 같은 예시 데이터·2026-10-25 고정 시각·문 상태, Chromium의 649×660 뷰포트로 이전/현재를 재현했다. 앱 760/761/800/896/1120px 및 위젯 390/320px도 확인했다.
- 11개 재현 환경의 런타임 오류와 외부 자산 요청은 0이었다. 아래 수치는 로컬 재현이며 사용자의 라이브 클라이언트 화면을 직접 읽은 결과는 아니다.
- [원시 측정 결과](miniature-kitchen/appearance-audit-results.json), 런타임 스크립트·HTML은 `/workspace/.notion-cloud/miniature-scene/appearance-audit-2026-10-25/`에 보관한다.

## 1. 냉장고와 배경의 확대 기준이 다르다

649px 위젯에서 냉장고 폭은 약 62.43% 커졌지만, 배경은 약 40.64% 확대됐다. `.room`의 `background-size:auto 100%`가 늘어난 장면 높이를 따라 배경을 별도로 확대한다. 배경에서 보이는 가로 범위는 원본의 약 69.45%에서 49.39%로 줄었다. 빈 설치 공간·선반·조리대의 위치가 냉장고와 같은 비율로 움직이지 않는다.

냉장고 폭은 `--fridge-focus-width`, 배경은 장면 높이, 소품은 별도 픽셀 크기를 사용한다. 넓은 앱의 요리 그림은 205px로 고정돼 본체 폭 대비 비율이 761px 화면에서는 약 72%, 1120px에서는 약 57%가 된다. 한 공간의 좌표와 축척을 공유하지 않아 배경 위에 물체를 각각 붙인 듯한 모습이 된다.

관련 코드: [배치 CSS](../designs/miniature-kitchen/scene.css)의 `.room`, `.item.meal`, `--fridge-focus-width`, `.is-compact .fridge-stage`.

## 3. 760px 경계에서 크기·구도가 급변한다

| 현재 앱, 높이 660px | 폭 760px | 폭 761px |
| --- | ---: | ---: |
| 본체 폭 | 440px | 284.77px |
| 본체 높이 | 767.30px | 496.61px |
| 장면 폭 | 732px | 840px |
| 장면 높이 | 843.30px | 560px |
| 처음 보이는 본체 | 약 59.56% | 100% |

[760px 화면](miniature-kitchen/appearance-app-760.png)과 [761px 화면](miniature-kitchen/appearance-app-761.png). 폭이 1px 늘어도 냉장고는 약 35.28% 작아진다. 동시에 탭·배경 범위·양념/조리대 노출도 바뀐다. 사용자가 미리보기 패널을 조금만 조절해도 다른 구도처럼 보일 수 있다.

관련 코드: [scene.js](../designs/miniature-kitchen/scene.js)의 `compact()`가 `innerWidth<=760`에서 클래스를 전환하고, 작은 화면용 440px 기준과 넓은 화면용 높이 89% 기준이 서로 다르다.

### 기존 가로 넘침에 새 버튼 겹침까지 추가됐다

761px 앱에서 장면 폭은 840px, 문서 폭은 868px로 화면보다 107px 넘친다. `aspect-ratio:3/2`와 `min-height:560px`의 조합이 최소 840px 폭의 장면을 만든다. 이 넘침은 [확대 전 761px](miniature-kitchen/appearance-before-app-761.png)에서도 같았으므로 최근 확대만의 원인으로 돌리지 않는다.

반면 버튼 겹침은 최근 `.kitchen-view`로 버튼을 분리하면서 생겼다. 현재 장면 폭은 840px이고 버튼 기준 컨테이너 폭은 705px라서 두 좌표계가 다르다. 본체 오른쪽은 x=338.89px인데 버튼이 x=310px에서 시작해 약 28.89px 겹친다. 이전 버튼은 x=364.19px에서 시작해 겹치지 않았다. 800px에서도 장면은 68px 넘치고 버튼은 본체에 약 13.30px 겹치며, 896px에서는 해당 넘침과 겹침이 사라진다.

## 4. 문은 평면 회전이며 원근 설정도 전달되지 않는다

현재 DOM에서 `.fridge-doors`의 `transform-style`은 `flat`이다. 브라우저 안에서만 원근을 `2400px`, `1100px`, `none`으로 바꾸어도 열린 문 사각형 수치는 모두 같았다. 첫 문은 x=37.93px, 폭=37.82px, 높이=412.80px로 유지됐다.

같은 브라우저에서 중간 컨테이너만 `preserve-3d`로 바꾸면 원근 2400px에서 문 폭이 62.73px, 1100px에서 99.31px로 변했다. 따라서 기존 계층이 원근 전달을 막는 것을 확인했다. 이 변경은 조사용 페이지에만 적용하고 저장하지 않았다. 실제 원근을 켜면 위치·잘림·겹침도 다시 바뀌므로 단독 수정으로 완료할 사항은 아니다.

확대 수정은 작은 화면의 문 각도도 112도에서 100도로 바꿨다. 평면 뒤판의 투영이 더 좁아져 큰 본체 옆에 길고 얇은 판처럼 보이는 효과가 강해진다. 평면화 구조는 확대 전에도 있었고, 각도·크기 변경으로 더 두드러진 부분과 구분한다.

## 5. 기능 검사의 통과 기준이 구도 문제를 잡지 못했다

기존 52개 검사는 실제로 통과했다. 다만 [검사 코드](../scripts/test_miniature_kitchen_browser.py)는 본체 폭이 400px 이상인지, 발 아래 간격이 맞는지, 문이 `.room` 안에 들어오는지, 버튼이 그림 밖에 있는지 등을 확인했다. `.room` 자체가 뷰포트보다 커지는 것은 막지 않는다. 클릭은 Playwright가 대상을 스크롤해 보여 주므로 처음 화면에서 버튼이 안 보이는 문제도 성공으로 남는다.

가로 넘침 검사도 있었지만 761/800px처럼 문제가 발생하는 경계 구간은 검사 대상이 아니었다. 따라서 이 결과는 동작·데이터 보존·이미지 로딩의 근거이고, 전체 장면의 구도·사용자 화면의 첫 인상·디자인 승인 근거가 아니다. 경계 양쪽과 첫 뷰포트 구도 검사가 빠져 있었다.

## 다음 수정의 기준

1. 배경·냉장고·재료·소품의 기준 공간과 축척을 함께 정한다.
2. 실제 미리보기의 폭과 높이를 기준으로 처음 보여야 할 영역과 조작 위치를 정한다.
3. 앱/위젯의 반응형 전환 전후에서 크기·위치·문 투영이 자연스럽게 이어지게 한다.
4. 문 계층·원근·뒤판을 함께 검토하고 같은 문 상태로 비교한다.
5. 기능 회귀와 별도로 첫 뷰포트·경계값 양쪽의 시각 검증을 남긴다.

이번 점검으로 새 구도나 디자인이 승인됐다는 의미는 아니다. 원인 분석·재현 증거만 추가했다.
