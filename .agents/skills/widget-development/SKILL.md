# 위젯 개발과 검증

[공통 규칙](../../../AGENTS.md)과 [개발 절차](../../../docs/development-workflow.md)를 먼저 읽는다. 사용자가 지정한 기능·확정 시안과 승인 범위가 이 스킬의 기본값보다 우선한다.

## 1. 작업을 구체화한다

1. 현재 브랜치·커밋·작업 파일을 확인하고 기능 브랜치를 사용한다. 기존 격리 체크아웃을 재사용한다. 별도 worktree는 사용자가 요청했을 때만 추가한다.
2. 실제 진입 HTML, 로드하는 JS·CSS·데이터, 저장 키, 관련 수집·게시 스크립트와 Actions의 경로 필터를 조사한다. 투자 레이더는 `stock-value-radar.html`과 호환 진입 주소부터 확인한다.
3. 바뀔 동작, 유지할 동작, 확인할 화면과 실패 상태를 짧게 정리한다. 합리적인 구현 선택이나 일반적인 로컬 검증 때문에 승인을 다시 요청하지 않는다.
4. 배포가 이번에 승인된 작업인지 구분한다. 명시적인 승인 없이 운영 설정·main·실제 사이트를 변경하지 않는다.

## 2. 기준 화면과 상태를 남긴다

- 편집 전에 관련 기존 테스트를 실행하고 결과를 기록한다. 기존 실패를 새 변경의 통과 결과로 감추지 않는다.
- 동일한 데이터·URL·화면 크기에서 기준 스크린샷과 실제 동작을 기록한다. 산출물은 기본적으로 `/tmp` 같은 체크아웃 밖에 둔다.
- 데스크톱·모바일·iframe 세 가지 조건을 명시한다. iframe은 Notion 임베드를 위한 대리 검증이며 실제 Notion UI 확인과 구분한다.
- 브라우저 저장은 독립 컨텍스트의 테스트 기록을 사용한다. 실제 사용자의 저장소를 지우거나 덮어쓰지 않는다.

## 3. 작은 범위로 구현한다

- 기존 승인 UI를 기준으로 절제된 색, 선명한 글자, 일정한 카드·여백·버튼 크기를 유지한다. 요구하지 않은 전체 디자인 변경을 추가하지 않는다.
- API나 데이터 오류를 성공·가짜 수치로 바꾸지 않는다. 사용 가능한 마지막 실제 자료와 실패·기준일을 정확히 표시한다.
- 기존 저장 기록·동기화·링크·쿼리·해시 호환성을 보존한다. 데이터 스키마가 달라지면 이전 저장 상태로 마이그레이션을 검증한다.
- 금융 수집 스케줄과 publisher의 변경 범위를 확인한다. 검증을 위해 실제 갱신·push·Pages 빌드 명령을 실행하지 않는다.

## 4. 실제로 실행하고 화면을 비교한다

저장소 루트에서 변경 검사 실행기를 사용한다.

```sh
python scripts/check_changed.py --base origin/main --head HEAD --working-tree --browser --artifacts /tmp/widget-checks
```

시스템 Chromium을 사용하는 클라우드 환경은 필요한 경우 `--executable /usr/bin/chromium`을 추가한다. 브라우저 의존성이 없으면 검증을 건너뛰어 성공 처리하지 말고 설치하거나 미검증 원인을 보고한다. 테스트 대상 변경과 브라우저 범위의 출력 보고서를 확인한다.

투자 레이더를 직접 확인할 때는 별도 터미널에서 로컬 서버를 실행한 뒤 아래 검사를 사용할 수 있다.

```sh
python -m http.server 8766 --bind 127.0.0.1
python scripts/test_radar_development_browser.py --base-url http://127.0.0.1:8766/ --artifacts /tmp/radar-after
```

서버는 첫 명령이 실행되는 터미널에 남겨 두고 두 번째 명령은 다른 터미널에서 실행한다. 기존 포트를 점유한 다른 프로세스를 임의로 종료하지 않는다.

실패를 발견하면 출력·화면·관련 코드를 통해 원인을 조사하고 수정한 범위의 검사를 다시 실행한다. 화면 전후 비교에서는 넘침뿐 아니라 비율·정렬·대비·읽기 순서도 확인한다. 원격 페이지, 외부 API, 실제 Notion처럼 실행하지 못한 검사는 구분해 남긴다.

## 5. PR로 전달한다

1. diff에서 의도하지 않은 데이터·설정·생성물 변경이 없는지 확인한다.
2. 작업 브랜치를 푸시하고 `.github/PULL_REQUEST_TEMPLATE.md`를 사용해 PR을 만든다. 자동 병합은 켜지 않는다.
3. 구현 내용, 검사별 통과·실패·미실행, 전후 화면, 데이터 보존과 금융 갱신 영향, 남은 제한을 PR과 완료 보고에 적는다.
4. API·인증·네트워크 때문에 PR 생성이 막히면 이미 완료한 구현과 검증을 보존하고 정확한 실패 단계를 보고한다. 존재하지 않는 PR이나 게시 성공을 만들어 쓰지 않는다.

PR 검사는 main 기반 Pages 자동 게시를 소급해 차단하지 않는다. 배포 게이트 전환은 별도의 승인 작업으로 다루고 기존 금융 갱신 작업의 연속성을 확인한다. 사용자 승인 뒤에도 검사한 커밋과 게시할 커밋이 같은지, 공개 사이트에 실제 반영됐는지 각각 검증한다.
