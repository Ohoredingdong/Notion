# 위젯 개발과 검증

위젯 수정·기능 추가·관련 자동화 개선에 사용한다. 처음 적용할 때 이 스킬을 사용한다고 짧게 알린다. 사용자 요청과 현재 세션의 승인 범위를 우선하며, 이 스킬 자체로 추가 승인을 요구하지 않는다. 운영 병합·배포는 사용자가 승인한 경우에만 진행한다.

## 1. 현재 상태와 영향 범위 기록

저장소 루트에서 시작한다.

```sh
git status --short
git branch --show-current
git diff --stat
```

기존 수정·미추적 파일과 현재 HEAD를 기록한다. 사용자가 만들던 작업을 정리하거나 덮어쓰지 않는다. 작업용 브랜치가 이미 있으면 재사용하고, `main`이면 별도 작업 브랜치를 만든다. 추가 worktree는 사용자가 요청할 때만 사용한다.

`rg`와 `rg --files`로 아래 연결을 추적한다.

- 진입 HTML → CSS/JavaScript → 가져오는 JSON/API → 연관 페이지·호환 주소.
- 입력·버튼 → 이벤트 처리 → 브라우저 저장 키·동기화 → 재로드 동작.
- 수집·가공 스크립트 → 테스트 → Actions trigger·권한 → stage/push/Pages 요청.

기존에 승인한 화면과 기능 요구사항을 먼저 정리한다. UI 기본 방향인 절제된 iOS 스타일을 이유로 승인된 구도·밀도·기능을 바꾸지 않는다.

투자 레이더의 기준 화면은 `stock-value-radar.html`이다. `stock-radar-dashboard.html`은 쿼리 문자열·해시를 유지해 기준 화면으로 이동하는 호환 주소이고, `stock-value-radar-advanced.html`은 보존된 심층 분석 화면이다. 현재 메인은 `assets/stock-radar-clean-bridge.js`, `assets/stock-radar-flow-v2.js`와 추가 참조 스크립트로 동작하며 종목 분석에 승인된 V6 화면을 사용한다. 설치용 스크립트나 오래된 UI 테스트를 현재 화면의 유일한 기준으로 삼지 않는다.

## 2. 수정 전 기준 화면과 데이터 확보

- 현재 작업 사본으로 로컬 서버를 띄워 기존 동작과 콘솔·요청 실패를 확인한다. 정적 위젯은 `python -m http.server 8765 --bind 127.0.0.1`로 실행할 수 있다. 이미 사용 중인 포트·프로세스는 유지한다.
- 브라우저의 동일한 화면 크기·테마·데이터·선택 상태에서 수정 전 화면을 캡처한다. 수정 중에도 기준 화면이 필요하면 관련 파일을 `/tmp/`에 복사해 별도 포트로 제공한다. 사용자 파일을 되돌려 기준 화면을 만들지 않는다.
- 데스크톱, 모바일, iframe 안의 노션 임베드 크기를 기록한다. iframe의 너비와 높이, 스크롤 가능 여부도 검증 대상이다. 실제 Notion 계정 안에서 열어보지 않았다면 그 범위는 미검증으로 남긴다.
- 관련 저장 키와 예시 기록의 구조를 조사한다. 브라우저 검증은 격리된 프로필에서 수행해 실제 사용자 브라우저 기록에 손대지 않는다.

## 3. 구현과 회귀 검사

요청한 동작을 필요한 범위에서 수정한다. 고정 숫자·무조건 성공 응답으로 수집·저장·생성 오류를 가리지 않는다. 저장 키와 형식을 보존하고 이행이 필요하면 구버전 기록을 읽는 경로를 검증한다.

변경된 파일과 관련 검사를 선택해 실행한다. [개발 환경 안내](../../../development.md)에 따라 의존성을 준비한다. 커밋한 브랜치 변경과 관련된 검사를 실행하려면 다음을 사용한다.

```sh
python scripts/dev_check.py --base origin/main --head HEAD --run --output /tmp/notion-dev-check/report.json
```

수정 중인 파일을 포함하려면 `--working-tree`를 추가한다. 기존 사용자 작업이 남아 있으면 이번 작업 파일을 `--files`로 명시한다. 예를 들어 아래 경로는 실제 수정한 파일 목록으로 바꾼다.

```sh
python scripts/dev_check.py --base origin/main --working-tree \
  --files stock-value-radar.html assets/stock-radar-flow-v2.js \
  --run --output /tmp/notion-dev-check/report.json
```

`--run` 또는 별칭 `--check`가 있어야 실제 검사를 실행한다. 계획만 출력한 결과를 통과로 보고하지 않는다. 관련 기능에 자동 선택 규칙이 없다면 필요한 검사를 직접 실행하고 그 누락을 선택 규칙에도 보완한다. 새 검사도 실제 사용자 동작·실패 조건을 확인해야 하며 구현과 동일한 문자열을 반복하는 검사만 추가하지 않는다.

투자 레이더·발행 로직에서 재사용할 기존 검사 예시는 다음과 같다. 실제 수정 범위에 맞게 골라 실행하고, 나열한 명령을 모두 실행했다고 보고하지 않는다.

```sh
python scripts/test_stock_radar_publish_protection.py
python -m unittest scripts.test_market_context -v
python scripts/test_widget_data_repairs.py
```

`test_widget_data_repairs.py`는 `beautifulsoup4`가 필요하며 임시 Git 저장소에서 동시 발행·오래된 자료 덮어쓰기 방지 등을 검사한다. 운영 수집기나 `publish_*.py`를 운영 저장소에서 직접 실행하는 것으로 대체하지 않는다.

JavaScript 변경에는 `node --check <수정한.js>`를 포함한다. Python 변경의 문법 검사 산출물이 기존 파일을 오염시키지 않도록 임시 캐시 경로를 사용한다. 문법 통과는 동작 검증 결과와 별도로 기록한다.

## 4. 실제 브라우저에서 변경 후 확인

현재 화면용 브라우저 검사는 자체 로컬 서버를 띄울 수 있다. Chromium이 설치된 환경에서 다음처럼 실행한다. 시스템 Chromium 경로가 다르면 실제 경로를 지정하고, Playwright 관리 브라우저를 사용하면 `--browser-executable`을 생략한다.

```sh
python scripts/test_stock_radar_canonical_browser.py \
  --browser-executable /usr/bin/chromium --output /tmp/notion-radar-browser
```

이미 실행 중인 서버는 `--base-url http://127.0.0.1:8765/`로 지정할 수 있다. 검사할 저장소 사본은 `--root`로 지정한다. 투자 레이더 외 위젯은 해당 기능의 브라우저 테스트를 선택하거나 같은 원칙으로 보완한다.

다음을 확인한다.

- 데스크톱과 모바일의 본문·설정·중요 버튼·포커스·스크롤·콘솔 오류.
- iframe 임베드에서 잘림·가로 넘침·내부 스크롤·주요 조작.
- 수정한 기능의 입력·선택·이동·저장과 재로드 후 복원.
- 데이터 누락·실패·저장 거부 시 오류 표시와 기존 기록 보존.
- 투자 레이더는 두 진입점, 종목·시장 선택, 즐겨찾기·조건 알림·모의 보유·심리 시장 선택 등 영향받는 기존 동작.

같은 조건으로 전후 스크린샷을 비교한다. 캡처만 생성하고 비교하지 않았으면 그 사실을 적는다. 고정 fixture나 요청 실패를 주입한 경우 테스트 이름·결과에 표시하고, 실제 제공처 데이터 검증과 구분한다.

실패하면 화면·콘솔·응답·재현 조건을 확인해 원인을 찾고 수정 후 다시 실행한다. 오래된 selector 문제라면 현행 기능을 검사하도록 테스트를 갱신한다. 사용자 기능의 회귀를 감추기 위해 검사를 제거·건너뛰거나 성공 조건을 약화하지 않는다.

## 5. 데이터 자동 갱신과 배포 영향 확인

`.github/workflows/`에는 금융 데이터를 일정에 따라 갱신하고 `main`에 직접 저장하는 작업이 있다. 테스트·CI 정책 변경 전에 변경된 workflow의 `on`, `permissions`, `concurrency`, 실행 분기, stage 목록과 Pages 요청을 읽는다.

- 일정·토큰 권한·동시 발행 보호와 기존 최신 데이터 보존 동작을 유지한다.
- 검증용 로컬 실행이 JSON/JSONL·보고서를 바꾸면 diff를 조사하고 작업 산출물과 운영 데이터를 구분한다. 기존 사용자 변경을 되돌리는 방식으로 정리하지 않는다.
- 수집 작업이 승인된 HTML을 덮어쓰지 않는지 게시 보호 검사를 실행한다.
- 테스트 실패를 배포 차단으로 연결하는 변경은 현재 main 직접 writer와 충돌하지 않는지 확인한다. 체크가 존재한다는 이유만으로 서버의 병합·Pages 배포가 실제 차단된다고 보고하지 않는다.
- 브랜치 보호·Pages 정책을 임의로 바꾸거나, 배포를 포함한 workflow를 시험 삼아 dispatch하지 않는다.

## 6. 작업 브랜치와 PR 마무리

```sh
git diff --check
git diff --stat
git status --short
```

시작할 때의 dirty 상태와 비교하고 사용자 작업을 보존했는지 확인한다. 정확한 작업 파일만 stage하며 `git add .`·`git add -A`는 사용하지 않는다. 운영 JSON/JSONL, 브라우저 산출물, 토큰·쿠키를 우연히 포함시키지 않는다.

PR은 [.github/pull_request_template.md](../../../.github/pull_request_template.md)를 따른다. 문제와 결과 동작, 실행 명령·결과, 전후 화면·브라우저 검증 증거, 사용자·금융 데이터 보존, 남은 제한을 포함한다. 결과 상태는 `통과 / 실패 / 건너뜀 / 미실행`으로 구분한다. CI는 실제 GitHub 실행 결과를 확인했을 때만 통과라고 적는다.

사용자가 승인하기 전에는 PR을 병합하거나 운영 사이트에 배포하지 않는다. PR을 만들 수 없는 환경이면 브랜치·변경 파일·검증 결과와 구체적인 차단 원인을 남기며, 생성하지 않은 PR 링크를 만들지 않는다.
