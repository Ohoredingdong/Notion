# 기존 위젯 수정

루트 [AGENTS.md](../../../AGENTS.md)와 [개발 절차](../../../docs/DEVELOPMENT.md)를 먼저 따른다. 현재 사용자 요청이 과거 문서·시안보다 우선한다. 스킬이 처음 적용되는 대화에서는 사용 사실을 짧게 알린다.

## 1. 현재 구현과 재현

- 기존 체크아웃의 git 상태·브랜치·기준 SHA를 기록하고 별도 작업 브랜치를 사용한다. 사용자 변경을 보존하며 명시적 요청 없이 worktree를 만들지 않는다.
- 요청 대상의 실제 HTML과 로드하는 JS/CSS/JSON, 이전 주소의 리다이렉트, 저장 키/스키마, 관련 테스트를 추적한다. 기능이 다른 앱의 코드를 이름만 보고 연결하지 않는다.
- 확정된 디자인과 사용자 요구를 식별한다. 시안은 기준으로 사용하되 예시 숫자·재료·기록을 실제 데이터에 채우지 않는다. 사용자에게 재설명을 요구하기 전에 연결된 자료와 기존 소스를 확인한다.
- 현재 결함을 실제 조작으로 재현하고 입력 데이터·시간·화면 크기·상태·기대 동작을 기록한다. 읽기 점검 중 reset, 실제 동기화 쓰기, 알림, 데이터 갱신·게시 스크립트를 실행하지 않는다.

## 2. 작은 범위의 구현

- 기존 확정 외형을 유지한다. 새 UI는 절제된 iOS 스타일과 명료한 글자·대비·상태색을 사용한다. 주요 조작을 쉽게 찾을 수 있게 하며 화면 축소·정보 숨김·가짜 성공 상태로 문제를 덮지 않는다.
- 기존 URL, 기능, 입력 값, localStorage 이름·형식·ID·수량·날짜를 보존한다. 저장/취소·새로고침·오류 복구가 필요한 흐름을 함께 다룬다. 사용자 기록을 이름만으로 테스트 데이터로 분류하지 않는다.
- 정책이나 스키마 변경이 필요하면 원본 보존, 명시적인 전환 조건, 복구 경로와 이전 실제 형식의 회귀를 구현한다. 새 샘플을 넣어 기존 기록이 정상처럼 보이게 만들지 않는다.

## 3. 자동 검사와 원인 확인

```bash
python scripts/dev_check.py --base origin/main --plan --output /tmp/notion-check
python scripts/dev_check.py --base origin/main --output /tmp/notion-check
```

관련 테스트가 빠져 있으면 실제 사용자 흐름·데이터 보존·실패 경로를 보호하는 검사를 보완한다. 낮은 영향의 단순 스타일 변경을 위해 구현을 그대로 복제하는 테스트를 만들 필요는 없다. 기존 테스트 실패는 같은 기준 SHA에서 재현해 환경·기존 실패·신규 회귀를 구분한다. 단언 삭제나 무조건 성공 처리 대신 원인을 고치고 해당 검사를 다시 실행한다.

## 4. 전후 화면과 브라우저

- 같은 자료·날짜·테마·조작 상태·뷰포트에서 수정 전후를 촬영한다. 테스트·캐시·스크린샷은 체크아웃 밖의 명시적 출력 폴더에 둔다.
- 데스크톱, 390px·320px 모바일, 요청된 Notion 임베드 크기의 iframe에서 첫 화면과 상세/탭/모달을 실제로 연다. 반응형 경계 양쪽도 확인한다.
- 사진/차트 비율, 정보 위계, 가로 넘침, 버튼 가림·겹침, 터치·키보드, 입력 중 상태, 저장/취소·재로드·오류를 확인한다. 디자인 판단은 실제 캡처를 직접 보고 수행한다.
- 기존 저장 fixture는 격리 브라우저에만 주입하고 조회 전후 원문·의도한 변경 범위를 비교한다. 개인 운영 기록을 QA에 사용하거나 공개 산출물에 넣지 않는다.
- localhost, 일반 HTTPS, iframe sandbox의 임시 저장, 실제 모바일/Notion 실행을 구분한다. 공개 URL은 HTTP 접근뿐 아니라 HTML 실행·요청 자산·주요 조작도 확인한다. 임시 미리보기의 기록을 영구 저장이라고 설명하지 않는다.

## 5. PR과 전달

최종 diff·산출물·입력 SHA와 검사 결과를 확인하고 검토용 PR을 준비한다. PR에는 실제 문제, 바뀐 동작, 검증과 미검증 범위를 적는다. UI 변경은 전후 화면을 포함한다. 사용자가 승인하기 전 자동 병합·운영 배포·브랜치 보호/배포 정책 변경은 하지 않는다. 코드 구현·테스트 통과·시안 승인·배포 완료를 각각 구분해 보고한다.

배포 전에는 해당 대상 SHA의 필수 검사 통과와 사용자 승인을 확인한다. 다른 커밋의 성공, 필수 검사 누락·실패, 미실행을 성공으로 취급하지 않는다.
