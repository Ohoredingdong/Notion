# 한끼의 부엌 — 전체 동선·상세 화면 명세

2026-11-04 · Asia/Seoul · **사용자 검토용 동작 설계 시안**

이 문서와 `flows.json`은 새 디자인의 화면·버튼·상태 규칙이다. 실제 앱 구현·OCR 실행·재고/지출 저장 완료를 뜻하지 않는다. 이미지와 수치는 설명용 예시이며 실제 사용자 기록을 복사하거나 수정하지 않았다. 소스·앱 파일은 변경하지 않았다.

하단 메뉴는 **냉장고 · 레시피 · 기록 · 내 부엌**이다. 상세 입력 화면은 뒤로/닫기로 돌아가며, 메뉴를 중복해서 쌓지 않는다. 모든 화살표는 **누르는 버튼 → 목적 화면 ID·이름**을 표시한다. 주황은 주요 동선, 회색은 돌아가기·보조 동선이며, 색을 데이터 저장 여부로 해석하지 않는다.

## C6 구매·지출의 두 상태

1. **구매 초안:** C5에서 진입한다. 실제 결제 금액과 날짜를 확인하고 「지출 저장」을 눌러 C4의 갱신된 월 식비로 돌아간다. 이때는 재고가 추가되지 않는다. 저장 전 「구매 재료 등록」은 비활성 상태이며 이유를 표시한다.
2. **저장된 영수증:** C4의 저장된 구매내역 행에서 「구매 내역 보기」를 눌러 C6로 재진입한다. 지출 저장 완료를 표시하고 같은 구매를 다시 지출로 저장하지 않는다. 이 상태에서 선택한 구매항목의 「구매 재료 등록」을 누르면 A3 사진2장으로 간다. A4 검수·확인 저장 전까지 재고는 바뀌지 않는다. 여러 품목은 하나씩 등록한다.

따라서 개요의 **「지출 저장 후 · 구매 재료 등록 → A3」**는 저장된 영수증 상태에만 해당한다. 이 조건은 이미지의 짧은 화살표 라벨과 `flows.json`의 `from_state`/`guard`로 함께 명시한다.

## 모든 화면의 버튼 → 다음 화면

## 예시 값의 일관성

- 날짜는2026년11월4일(수)이다. 우유500mL·기한2026.11.10은 설명용이다.
- 계란 볶음밥1회분은 입력값 예시455kcal, 탄수화물60g·단백질20g·지방15g이다. A1/A5의 기존 섭취100/35/20g은720kcal(아침 직접 기록1끼)와 일치한다. B5 실제 식사 저장 후 B6/C1은160/55/35g·1175kcal·2끼로 갱신된다. C1에는 아침 직접 기록720kcal와 점심 계란 볶음밥455kcal를 함께 표시하며 C3 월간 식사 횟수도2회다. 재고는 계란6→4개, 밥2→1공기 예시를 사용한다.
- 예산300,000원, 기존 실제 지출128,000원, 이번 실제 결제18,300원이다. 지출 저장 후 실제 지출146,300원, 남은 예산153,700원이다. 장보기 예상액18,300원은 저장 전 실제 지출에 포함하지 않는다.
- 첫 요리1/8·꾸밈권+1은 같은 요리(recipe_id)의 첫 실제 기록에1회 지급한다. 취소/재기록으로 같은 요리에 다시 지급하지 않는다. 새 보상 소품 비용1은 D5 적용 때 차감해1→0이 된다. 취소는1을 유지한다.

## 검토할 오류·경계 상태

- 사진이1장뿐이면 글자 읽기를 활성화하지 않는다. 읽지 못한 값은 확인 필요로 남기고 직접 수정할 수 있다.
- 인식 실패·미입력 영양·알 수 없는 가격을0 또는 임의의 정확한 수치로 바꾸지 않는다.
- 재고 부족·단위 미확인 상태는 차감 검수에서 해결한다. 음수 재고와 추정 단위 변환을 허용하지 않는다.
- 계획 저장과 실제 식사 저장의 버튼/설명을 다르게 유지한다. 같은 계획을 두 번 먹은 기록으로 확정하지 않는다.
- 실행 취소가 다른 식사·후속 재고 수정과 충돌하면 조용히 덮어쓰지 않는다. 해당 거래만 복구 가능할 때 수행한다.
- C6 저장 실패 시 초안과 영수증을 유지하고 월 합계는 바꾸지 않는다. 재진입/중복 탭으로 지출을 이중 추가하지 않는다.
- D5 적용 실패 시 소품·비용·배치 중 일부만 확정하지 않는다. 취소는 편집 전 기준을 복원한다.
- 식사 취소/재기록, 도감 재조회, 보상 상세 재조회로 첫 요리 보상을 다시 지급하지 않는다.
